# 超时与降级说明（阶段3 提交物第 3 项）

> 任务书步骤4 的提交物：`outputs/stage03_demo.json`、**三类链路 trace**、**超时与降级说明**。
> 这个文件就是第 3 项：**哪里会超时、超时之后怎么降级、响应里哪些字段会变、证据在哪、怎么现场验证**。
> 所有数字来自 `outputs/stage03_demo.json` 与本机实测。

---

## 1. 一句话版本

> 上游（隔壁模块一推荐服务）超时或不可用时，**不报错、不空手**：
> 记一条警告 `UPSTREAM_TIMEOUT`，把候选来源从「上游分数」换成「热门商品」，
> 用户的条件（品类/颜色/预算）继续生效，响应标 `degraded=true`，商品照常返回。

---

## 2. 哪些地方会“超时”（各自超时值不同）

| 位置 | 超时值 | 配置项 | 超时后发生什么 |
| --- | --- | --- | --- |
| 模块一 HTTP 推荐接口 | **2 秒**（自动接入真实模块一时改成 5 秒） | `IRA_TIMEOUT` / `upstream_timeout_seconds` | **降级**：改成离线热门召回，响应带 `UPSTREAM_TIMEOUT` |
| 模块一服务启动等待 | **20 秒** | 代码固定（`module_one.py`） | 启动失败 → `app.py` 回退离线演示，stderr 打印回退警告 |
| 模块二语音/视觉/手势识别 | **180 秒** | `IRA_MEDIA_TIMEOUT` | 媒体接口返回 503 + 错误码，页面保留手动输入 |

> 本阶段（阶段3）要说明的是第一行：**推荐上游超时 → 降级为热门召回**。

---

## 3. 降级一共分五层（本阶段是第 1 层）

| 层 | 什么坏了 | 怎么降级 | 用户看到 |
| --- | --- | --- | --- |
| **1. 推荐上游** | 模块一超时/不可用/返回格式错 | 候选改用 `popularity`（热门）路由，`mode=offline_demo` | 商品照常出，响应 `degraded=true` + `warnings[0].code` |
| 2. 模块一整体不可用 | 没有同级项目/启动失败 | 用仓库自带 18 件合成目录 | 页面能开、能推荐，只是换成了演示商品 |
| 3. 模块二不可用 | 没有 `.venv`/模型/超时 | 语音视觉手势接口 503 | 页面保留手动转写、标签、手势输入 |
| 4. 解释证据不足 | 商品属性缺/证据不一致 | **该条**解释降级（`citations=[]`、`code=INSUFFICIENT_EVIDENCE`/`EVIDENCE_MISMATCH`） | 其它商品正常，这一条不给解释、也不编造 |
| 5. 硬约束空集 | 条件太苛刻（如预算 1 元买耳机） | **不降级**：不放宽条件，返回 `empty` + 提示调整 | 看到「请调整条件或撤销上一步」 |

> 第 5 层严格说是“边界处理”而不是“故障降级”，放一起说是因为它们都属于“拿不到理想结果时的正确姿势”。

## 4. 阶段3 的超时降级是怎么发生的（代码链路）

```text
RecommendationAdapter._recall_upstream(request)          recommendation.py L146
    │  调 self.remote.recall(request)
    │  上游超时 / 连不上 / 返回格式错
    ▼
except (AdapterError, ContractError, OSError, TimeoutError)   L185
    │  把异常翻译成一条警告（不向上抛）
    ▼
return {}, [{'code': 'UPSTREAM_TIMEOUT', ...}], 'offline_demo'    L187–188
    │
    ▼
recommend()：routes 仍然用 popularity 铺满全目录 → 硬约束过滤 → 打分 → 排序
    │          （上游这一项分数为 0，其它五项照常）
    ▼
Orchestrator：response['warnings'] = diagnostic['warnings']       orchestrator.py L214
             response['degraded'] = bool(warnings)                L215  ← 有警告就算降级
             response['mode'] = 'offline_demo'                     L216
    ▼
返回 200 + 正常商品列表（不是 500，也不是空列表）
```

**超时是怎么“注入”出来的（验收用）**：`scripts/03_orchestrator_demo.py` L17 的 `TimeoutRemote`，
它的 `recall()` 无论请求什么都抛 `AdapterError('UPSTREAM_TIMEOUT', ...)`（L38），
再把它传给 `RecommendationAdapter(settings, TimeoutRemote())`，就等价于“上游必超时”。

## 5. 响应里哪些字段变了（正常 vs 超时，真实值）

| 字段 | 正常链路 | 超时降级后 | 说明 |
| --- | --- | --- | --- |
| `status` | `ok` | `ok` | **降级不是失败**，仍返回 200 |
| `warnings[0].code` | `OFFLINE_DEMO` | **`UPSTREAM_TIMEOUT`** | 这是唯一的关键区别 |
| `degraded` | `true` | `true` | ⚠️ 离线演示模式下正常链路也带 OFFLINE_DEMO 警告，所以 `degraded` 两边都是 true；**对比要看 warnings 里的 code** |
| `mode` | `offline_demo` | `offline_demo` | 都走离线召回 |
| `items` 数量 | 2 件 | **2 件** | 结果数量不变 |
| `items[0].sources` | `['category','popularity']` | **`['category','popularity']`** | 证明走的是热门兜底 |
| `items[0].score_breakdown.upstream` | 0 | 0 | 上游没参与打分 |
| 会话约束 `context.constraints` | `{品类:背包,颜色:蓝色,预算≤300}` | **完全一样** | 硬约束没被降级影响 |

实测对比（本机跑出来的）：

```text
正常  : ok | degraded=True | warnings=['OFFLINE_DEMO']    | items=2 | sources=['category','popularity']
超时后: ok | degraded=True | warnings=['UPSTREAM_TIMEOUT'] | items=2 | sources=['category','popularity']
```

## 7. 为什么这样设计（被问“为什么不直接报错”）

1. **用户优先**：上游只是“更好的候选来源”，不是唯一来源；它挂了不该让用户什么都拿不到。
2. **条件不能变**：降级只换“从哪拿候选”，绝不改用户的品类/颜色/预算——否则就是偷偷降低服务质量。
3. **可解释**：`warnings[].code` 明确写出原因，`sources` 明确写出“这批结果来自热门”，前端可以提示“已降级”。
4. **可恢复**：下次请求上游恢复了，`mode` 自动回到 `hybrid`，不需要重启服务。

## 9. 边界与已知限制（讲清楚反而加分）

- **只降级“上游异常”，不掩盖程序 bug**：上游超时/不可用走 warnings；代码本身抛未预期异常走 `INTERNAL_ERROR`（500），不会伪装成降级。
- **超时值可调**：默认 2 秒（`IRA_TIMEOUT`），自动接入真实模块一时放宽到 5 秒；都是配置，不是写死。
- **离线演示模式下正常链路也是 `degraded=true`**（原因码 `OFFLINE_DEMO`）——所以判别降级要看 `warnings[].code`，不能只看布尔值。
- **降级不缓存**：每次请求都会重新尝试上游，上游恢复后自动回到 `hybrid`。
- **降级不等于没影响**：结果是“热门排序”，针对性会比真实排序弱；`sources` 里没有 `module_one_http` 就是提示。
