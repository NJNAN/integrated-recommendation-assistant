## 3. 文件二：`web_system/service.py`（排序与分页的真正实现）

### 3.1 `RecommendationService.__init__(score_path, catalog_path, neighbors_path, db_path)` · L55

**参数**：

| 参数 | 类型 | 含义 |
| --- | --- | --- |
| `score_path` | `Path` | 冻结排序 CSV |
| `catalog_path` | `Path` | 商品表 CSV |
| `neighbors_path` | `Path` | 相似索引 JSON |
| `db_path` | `Path` | sqlite 路径（没有会自动建库建表） |

**返回**：无。构造完就有：`self.rankings`、`self.catalog`、`self.neighbors`、`self.global_ranking`、`self.connection`。

### 3.2 `_load_rankings(path)` · L66（**重点，上游分数的真正来源**）

**参数**：`path` —— 冻结排序 CSV（三列：`user_id,item_id,score`）。

**返回**：`dict` → `{用户ID: [(商品ID, 0~1 的分), …]}`，已按分数从高到低排好。

**怎么做**（这就是为什么我们拿到的分数是 0~1，而不是 CSV 里的负数）：

1. 按 `user_id` 分组收集 `(item_id, 原始 score)`（原始分可能是 `-95`、`-24` 这种）；
2. 每组按 `(-score, item_id)` 排序，得到名次；
3. **按名次归一化**：第 0 名 = `1.0`，最后一名 = `0.0`，
   公式 `1.0 - index / (n-1)`。用户 `14911` 有 344 条 → 相邻两名差 `1/343 ≈ 0.002915`。

> ⚠️ 这点很容易讲错：CSV 里是负数，但**服务返回给我们的是 0~1 的排名归一化分**。
> 我们实测：用户 `14911.0` 的候选分数是 `1.0, 0.997085, 0.994169, …`。

### 3.3 `_load_catalog(path)` · L81 —— `{item_id: {item_id,name,description,category}}`

### 3.4 `_global_ranking()` · L95

把**所有用户**的归一化分按商品求平均，作为“冷启动兜底”（某个用户没有排名时用）。
返回 `[(item_id, 平均分), …]`，按分数降序。

### 3.5 `_seed_database()` · L107

建库时写入三类基础数据（`INSERT OR IGNORE`，重复跑不会重复插）：

- `users`：每个有排名的用户写一条 `"{user_id}.0"`（所以我们的演示账号是 `14911.0`）；
- `products`：排名里出现的商品；
- `auth_accounts`：三个演示账号 + `generate_password_hash(密码)`。

### 3.6 `_ranking_user_id(user_id)` · L127

**参数**：`user_id`（我们传的是 `14911.0`）。
**返回**：去掉 `.0` 后缀的字符串（`14911`）。
**为什么**：CSV 里是 `14911`，我们账号是 `14911.0`，靠这个函数对上。

### 3.7 `account(username)` · L131 / `product(item_id)` · L137

- `account(username)` → 账号行 `(username, user_id, display_name, password_hash)`，或 `None`；
- `product(item_id)` → 商品字典（不在目录时给“精选商品 + 该商品暂缺目录描述”的兜底）。

### 3.8 `recommendations(user_id, cursor, limit, exclude)` · L160（**我们拿到的就是这个**）

**参数**：

| 参数 | 类型 | 含义 |
| --- | --- | --- |
| `user_id` | `str` | 登录用户（`14911.0`） |
| `cursor` | `int` | 从第几条开始（分页游标） |
| `limit` | `int` | 一次返回几条（我们传 24） |
| `exclude` | `set[str]` | 要跳过的商品（点过“不喜欢”的） |

**返回**：`{items, session_id, next_cursor, has_more, model_version}`；
每个 item = 商品属性 + `score`（0~1）+ `source_type=oblivionis_v2` + `reason`（“用户内融合排名第 N 位”）。

**怎么做**：

1. 取该用户的排名（缓存 90 秒；没有就用 `global_ranking`）；
2. 从 `cursor` 开始往后扫，跳过 `exclude` 里的、跳过不在目录里的，凑够 `limit` 条；
3. 每条转成 `{**product(item_id), score: round(score,6), source_type, reason_code, reason}`；
4. 写一张 `recommendation_sessions`（本次请求）和若干 `recommendation_items`（本次返回的商品与名次）；
5. 返回 `next_cursor = 扫到的位置`，`has_more = 后面还有没有`。

### 3.9 我们**没用到**的两个方法（问到了知道是什么就行）

- `similar(item_id, limit, exclude)`（L202）：用 `item_neighbors.json` 返回相似商品；
- `feedback(user_id, payload)`（L235）：写 `feedback_events` 表。**我们的点赞/点踩不走这里**。

## 8. 五个高概率追问

**Q1：上游分数是怎么来的？**
> 模块一发布包里有冻结排序 CSV（三列 user_id/item_id/score）。服务启动时 `_load_rankings`
> 按分数排序后按名次归一化成 0~1（第一名 1.0，最后一名 0.0）。我们把它作为六项打分里的 `upstream` 一项。

**Q2：为什么候选是 317 个，不是 2,208 个？**
> 只返回该用户排名表里的商品（14911 有 344 条），再排掉不在商品目录里的和用户点过“不喜欢”的，剩 317 个。

**Q3：为什么要分页（cursor/limit）？**
> 模块一一次最多返回 24 条（我们的 `max_top_k`），我们用 `cursor` 循环翻页直到 `has_more=false`，
> 最多取 2,000 条（`recommender_max_candidates`）。游标不前进就当协议错误（`INVALID_UPSTREAM`）。

**Q4：为什么我们的 user_id 是 `14911.0`？**
> 模块一建库时把有排名的用户写成 `"{user_id}.0"`，而 CSV 里是 `14911`；
> 服务用 `_ranking_user_id()` 去掉 `.0` 后缀去匹配 CSV，所以我们发 `14911.0` 能对上。

**Q5：我们的点赞会写进模块一的数据库吗？**
> 不会。点赞/点踩只写我们自己的会话偏好（`assistant/feedback.py`），用于当前会话重排；
> 模块一的 `/api/feedback` 接口我们没调用。两边数据不互相污染，模块一不用跟着我们的会话状态跑。

## 9. 口播（90 秒，可直接念）

> 模块一也是我们组做的，但阶段3 只用到它的一小块：一个 Flask 服务加三个数据文件。
> 我们调三个接口：`/api/auth/login` 登录、`/api/recommendations` 分页拿候选、`/api/health` 判断服务就绪。
> 服务里最关键的是 `_load_rankings`：它读冻结排序 CSV，按分数排好序之后**按名次归一化成 0~1**，
> 第一名 1.0、最后一名 0.0；我们再把这一项当六项打分里的 upstream。
> 分页方面，我们每次要 24 条，用 cursor 翻页直到 has_more 为 false，最多 2,000 条。
> 实测用户 14911 有 344 条排序、返回 317 个候选，分数从 1.0 到 0，相邻差 0.0029——
> 所以反馈 +2.5 在真实模式下也能把商品顶到第一。
> 边界是：我们只调公开 HTTP 接口，不 import 模块一内部代码；点赞只写我们自己的会话，不写模块一数据库。
