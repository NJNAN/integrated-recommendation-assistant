## 2. `assistant/orchestrator.py`（254 行）

### 2.1 这个文件是干嘛的

它是整个系统的**唯一入口**。一条请求进来，它按固定顺序把各个模块串起来：
校验请求格式 → 让成员2 理解意图 → 取出这桌的点单记录（会话）→ 处理结束/撤销/冲突/追问 →
组装推荐请求 → 调你的推荐模块 → 让成员4 写解释 → 返回统一响应。
中途每一步都往 `trace` 里记一条流水账；出错就用进来时存的会话快照回滚。

### 2.2 函数清单

| 行号 | 函数 | 一句话 |
| --- | --- | --- |
| L25 | `__init__(settings, recommender=None, store=None)` | 装配三个依赖 + 一把锁 |
| L48 | `handle(data)` | 唯一对外入口：加锁 → 交给 `_handle` |
| L67 | `_handle(data)` | 真正的主链路（12 步） |
| L94 | 内部函数 `record(stage, value)` | 记一条 trace |
| L111 | 内部函数 `finish(status, message)` | 统一收尾 |

### 2.3 `__init__(self, settings, recommender=None, store=None)` · L25

**干什么**：把编排器需要的三个东西装进来，并创建一把锁。

**参数**：

| 参数 | 类型 | 含义 / 从哪来 / 取值 |
| --- | --- | --- |
| `settings` | `Settings` | 全局配置对象。这里主要用它的 `visual_threshold`（视觉标签阈值 0.7），传给理解模块 |
| `recommender` | 可选，默认 `None` | 推荐器，必须有 `.catalog` 和 `.recommend()`。传 `None` 就自动建 `RecommendationAdapter(settings)`；**测试/验收时传一个假的**，用来注入“上游超时” |
| `store` | 可选，默认 `None` | 会话仓库，必须有 `.get()` / `.end()`。传 `None` 就用内存会话 `SessionStore(settings)`（带 30 分钟 TTL） |

**返回**：没有返回值（构造函数）。

**怎么做**：

1. `self.recommender = recommender or RecommendationAdapter(settings)` —— 没给就自己建。
2. `self.store = store or SessionStore(settings)` —— 同上。
3. `self.lock = RLock()` —— 可重入锁。因为 HTTP 服务是多线程的，加锁后同一进程内一次只处理一个请求，
   否则两个用户的条件会互相覆盖。

**会出错吗**：一般不会；如果 `settings.catalog_path` 的目录坏了，会在这行抛 `INVALID_CATALOG`（提前失败）。

**口播**：
> `__init__` 接收三个参数：配置、推荐器、会话仓库。后两个允许传空，空了我自己建，这样测试时可以换成假的。

### 2.4 `handle(self, data)` · L48

**干什么**：对外唯一入口，负责“加锁”。

**参数**：

| 参数 | 类型 | 含义 / 从哪来 / 取值 |
| --- | --- | --- |
| `data` | `dict` | 原始事件 JSON，字段：`trace_id / user_id / session_id / timestamp / source / payload`。来自 HTTP 的 `POST /api/events` |

**返回**：`dict`，统一响应（字段见 2.5 的说明）。

**怎么做**：

```python
with self.lock:            # 上锁：一次只处理一个
    return self._handle(data)   # 交给主链路
```

**会出错吗**：不向外抛异常，所有错误都由 `_handle` 转成 `status='error'`。

**口播**：
> `handle` 只有两行：上锁，然后调用 `_handle`。上锁是为了多线程下不串会话。

### 2.5 `_handle(self, data)` · L67（最重要，讲 2 分钟）

**干什么**：真正的 12 步主链路。

**参数**：同 `handle(data)`。

**返回**：`dict`，统一响应，固定字段：

| 字段 | 含义 |
| --- | --- |
| `trace_id` | 全链路追踪号 |
| `status` | 六种之一：`ok / empty / needs_clarification / conflict / ended / error` |
| `message` | 给用户看的中文提示 |
| `items` | 商品列表（每件含 `sources`/`score`/`score_breakdown`/`evidence`/`explanation`） |
| `context` | 会话快照：约束、偏好、最近展示商品、TopK |
| `degraded` + `warnings` | 是否降级、降级原因码 |
| `error` | 只有出错时非空：`{code, message}` |
| `trace` | 7 段流水账 |
| `elapsed_ms` | 总耗时 |

**怎么做（12 步，行号可以指给老师）**：

| 步 | 怎么做 | 行号 |
| --- | --- | --- |
| ① | `InteractionEvent.from_dict(data)` 校验事件；失败 → `INVALID_EVENT` | L128 |
| ② | `understand(event, settings.visual_threshold)` 得到意图、槽位、缺失、冲突 | L133 |
| ③ | `store.get(user_id, session_id)` 取会话；`ctx.snapshot()` **先存快照**（为了回滚） | L137 |
| ④ | `action` 是 `end/reset` → 清会话，返回 `ended` | L142 |
| ⑤ | `action` 是 `undo` → `ctx.undo()` 撤销上一轮约束 | L149 |
| ⑥ | `intent.conflicts` 非空（同轮自相矛盾）→ 返回 `conflict` | L153 |
| ⑦ | 用户给了预算但币种和目录不一致（人民币 vs 英镑）→ 返回 `needs_clarification` | L159 |
| ⑧ | `intent.missing` 非空（如“找类似的”没给商品）→ 返回 `needs_clarification` | L172 |
| ⑨ | `ctx.merge(slots, evidence)` 合并约束；预算下界 > 上界 → `conflict` | L180 |
| ⑩ | 反馈分支：`apply_feedback(ctx, item_id, ±1)`；普通分支：`catalog.get(target)` 校验目标商品存在 | L187 |
| ⑪ | 组装 `RecommendationRequest` → `recommend()` → 逐条 `explain()` → 写 `last_item_ids` | L204 |
| ⑫ | 空集 → `empty`；对比/反馈/普通三种文案 → `ok` | L227 |

**出错时怎么做**（两条路径）：

- L237 `except ContractError`：业务/校验错误 → `error.code` 原样返回，并 `ctx.restore(snapshot)` 回滚；
- L246 `except Exception`：未预期异常 → 统一 `INTERNAL_ERROR`，同样回滚，不泄露内部细节。

**口播**：
> `_handle` 是主链路。我按 ①~⑫ 编了号：①校验事件、②理解意图、③取会话并存快照、
> ④处理结束、⑤撤销、⑥同轮冲突、⑦币种、⑧缺槽位、⑨合并约束、⑩反馈或校验目标商品、
> ⑪组装请求调推荐再调解释、⑫收尾。
> 任何一步抛业务错误，就回滚到 ③ 存的快照，所以失败请求不会污染会话；
> 上游超时不算错误，只写 warnings 和 degraded。

### 2.6 两个内部小函数

**`record(stage, value)` · L94**

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `stage` | `str` | 阶段名，只允许：`event / intent / context / request / recall_and_ranking / explanation / result / error` |
| `value` | 任意可 JSON 序列化 | 这个阶段的数据，例如事件字典、意图字典、请求字典、召回诊断信息 |

做法：往 `response['trace']` 追加 `{trace_id, stage, elapsed_ms, data}`，`elapsed_ms` 是相对本次请求开始的时间。

**`finish(status, message)` · L111**

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `status` | `str` | 六种状态之一 |
| `message` | `str` | 给用户看的中文提示，例如「找到 2 件符合条件的商品。」 |

做法：写 `status`/`message`/`elapsed_ms`，再补一条 `result` 阶段的 trace，返回同一个响应对象。

### 2.7 本文件口播（60 秒，可直接念）

> 这个文件是总调度：`__init__` 装配配置、推荐器、会话仓库和一把锁；`handle` 加锁后交给 `_handle`；
> `_handle` 里是 12 步主链路，每步都会写一条 trace，出错就用第 3 步存的会话快照回滚。
> 里面还有两个小工具：`record` 记流水账，`finish` 统一收尾（写状态、文案、耗时）。

### 3.3 `Catalog.__init__(self, path)` · L26

**干什么**：把商品目录 JSON 读进内存，顺手校验每个字段；不合法直接失败，不带着脏数据跑。

**参数**：

| 参数 | 类型 | 含义 / 从哪来 / 取值 |
| --- | --- | --- |
| `path` | `str \| Path` | 目录 JSON 路径。来自 `settings.catalog_path`：演示模式是 `data/catalog.json`（18 件），真实模式是 `data/module_one_catalog.json`（2,208 件） |

**返回**：无。结果落在属性上：

- `self.items`：`{商品ID: 商品行}`；
- `self.dataset / self.currency / self.real / self.price_notice`：数据集名、币种（CNY/GBP）、
  是否真实目录、价格口径说明。

**怎么做**：

1. `json.loads(路径.read_text())`，取 `document['items']`；
2. 逐个商品检查：`item_id/name/category/color` 不能空；`price` 允许 `None`，但必须标 `price_kind='missing'`
   且是真实目录；`popularity` 在 0~1；`tags` 是字符串数组；`visual_labels` 里每个标签有 `label` 和 0~1 的 `confidence`；
3. 商品 ID 不能重复；给缺省字段补默认值；存进 `self.items`。

**会出错吗**：任何一步不对 → `ContractError(code='INVALID_CATALOG')`（HTTP 400）。

**口播**：
> `Catalog.__init__` 接收一个路径，读 JSON 并逐字段校验；价格可以为空，但必须明确标注 `missing` 且来自真实目录。
> 有问题统一报 `INVALID_CATALOG`，不会带着脏数据往下跑。

### 3.6 `_recall_upstream(self, request)` · L146

**干什么**：向模块一要候选（登录 + 翻页由 `HTTPRecommender` 完成），把结果整理成
`{商品ID: 分数}`；任何失败都**不抛异常**，只返回警告。

**参数**：

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `request` | `RecommendationRequest` | 本函数只用到 `user_id`（模块一按用户推）和 `trace_id`（拼进 HTTP 头） |

**返回**：`tuple` 三个值 → `(scores, warnings, mode)`

| 值 | 类型 | 含义 |
| --- | --- | --- |
| `scores` | `dict` | `{商品ID: 上游分数}`，只留本目录里有的；同 ID 多次出现取最高分 |
| `warnings` | `list[dict]` | 降级说明，如 `[{'code':'UPSTREAM_TIMEOUT','message':'…'}]`；成功时是空列表 |
| `mode` | `str` | `'hybrid'`（上游成功）或 `'offline_demo'`（没配/失败/降级） |

**怎么做**：

1. `self.remote is None` → 直接返回 `({}, [OFFLINE_DEMO 警告], 'offline_demo')`；
2. 调 `self.remote.recall(request)`；
3. 逐行校验：必须有字符串 `item_id`，`score` 必须是 −1000~1000 的有限数；只保留本目录存在的 ID；
   上游给了候选但一个都不在本目录 → 报协议不匹配（转成 `INVALID_UPSTREAM` 警告）；
4. 成功返回 `(scores, [], 'hybrid')`；
5. `except (AdapterError, ContractError, OSError, TimeoutError)` → 按异常码返回 `({}, [警告], 'offline_demo')`。

**会出错吗**：不向外抛。上游超时/连不上/格式错都变成 `warnings`。

**口播**：
> `_recall_upstream` 接收推荐请求，只用到 `user_id` 和 `trace_id`。返回三样：分数表、警告、模式。
> 没配上游、超时、格式错，都只返回警告并降级，不会把异常抛给编排层。

### 3.7 `_hard_failures(product, constraints)` · L191（静态方法）

**干什么**：判断一件商品是否违反**硬约束**（违反就不许推，跟分数无关）。

**参数**：

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `product` | `dict` | 目录里的一行商品；只读 `category`、`color`、`price`（`None` 表示缺失） |
| `constraints` | `dict` | 会话约束，可能含 `category / color / budget_min / budget_max`（其它键不参与） |

**返回**：`list[str]`，失败原因，空列表表示通过。可能的元素：
`'category'`、`'color'`、`'missing_price'`（没价格但用户给了预算）、`'budget'`（超出下限或上限）。

**怎么做**：

1. 品类、颜色：约束给了且商品不相等 → 记 `category` / `color`；
2. 价格是 `None` 且用户给了预算 → 记 `missing_price`；
3. 价格超出 `[budget_min, budget_max]` → 记 `budget`；
4. 返回原因列表（可能同时多个，例如 `['category','color','budget']`）。

**口播**：
> 这是四个硬约束：品类、颜色、缺失价格、预算。返回一串原因，空列表就放行。
> 它在打分之前执行，所以分数再高也过不去。

### 3.8 `_score_breakdown(self, request, product, targets, upstream, mode, constraints)` · L225

**干什么**：给一个候选算六项分数，六项相加就是总分。

**参数**：

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `request` | `RecommendationRequest` | 用到 `intent`（只有 `similar` 才算相似度）、`preferences`（`{商品ID: ±1}`）、`trace_id`（不用算分） |
| `product` | `dict` | 候选商品行，读到 `item_id / category / tags / popularity` |
| `targets` | `list[dict]` | 用户点名的商品行（`similar` 时用 `targets[0]` 算相似度；其它意图传空列表） |
| `upstream` | `dict` | `{商品ID: 上游分数}`，离线时是 `{}` |
| `mode` | `str` | `'hybrid'` 或 `'offline_demo'`；真实目录 + hybrid 时热门项记 0 |
| `constraints` | `dict` | 会话约束；这里只读 `recipient` / `scene`（软偏好） |

**返回**：`dict`，六个键，都 `round` 到 6 位：

| 键 | 公式 | 人话 |
| --- | --- | --- |
| `popularity` | `0.4 × popularity`（真实目录 hybrid 时 0） | 越热门越靠前 |
| `context` | `0.2 × (对象命中 + 场景命中)` | 符合“送朋友/通勤”加分 |
| `similarity` | `0.3 × 同品类 + 0.1 × 共同标签数` | 只在“找相似”时算 |
| `upstream` | `0.3 × 上游分数`（真实模式 1.0） | 借模块一的排序 |
| `feedback` | `2.5 × 该商品偏好(±1)` | 点赞/倒踩 |
| `tag_affinity` | `0.06 × Σ 共同标签数 × 符号` | 喜欢一个商品会带动同类 |

**怎么做**：按上面六行逐个算，最后统一 `round(…, 6)` 返回。为什么要 round：
浮点累加会留 `0.36800000000000005` 这种尾巴，round 后 JSON 才能稳定比对。

**口播**：
> 六项打分：热门 0.4、场景 0.2、相似 0.3+0.1、上游 0.3（真实模式 1.0）、反馈 2.5、标签 0.06。
> 每项都单独返回，所以“为什么它排第一”永远答得出来。

### 3.9 `_evidence(self, request, product, sources, constraints)` · L279

**干什么**：给一件商品准备“证据包”，解释模块只能读这个包里的内容。

**参数**：

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `request` | `RecommendationRequest` | 只用 `trace_id`，写进证据包便于追溯 |
| `product` | `dict` | 商品行：name/price/category/color/description，真实目录还有 price_source/color_source |
| `sources` | `set \| list` | 召回来源集合，例如 `{'popularity','category'}`；内部会 `sorted()` 保证顺序稳定 |
| `constraints` | `dict` | 会话约束，用来算“命中了哪些条件” |

**返回**：`EvidencePack`（契约结构），字段：

- `trace_id / item_id`：标识；
- `attributes`：名称、价格、品类、颜色、币种、价格类型；
- `sources`：来源列表；
- `matched_constraints`：命中的约束；
- `visual_labels`：**只保留置信度 ≥ 0.7** 的标签；
- `snippets`：证据片段，id 形如 `catalog:<商品ID>:attributes | :description | :provenance`。

**怎么做**：先装 `attributes` → 造 `attributes` 片段（有描述再加一条；真实目录加 `provenance`）→
过滤低置信标签 → 计算命中约束 → 构造 `EvidencePack`。

**口播**：
> 证据包就是给每件商品做个小档案袋：属性、来源、命中条件、证据片段。
> 片段 id 一定带商品 ID 前缀，解释模块靠它校验“引用是不是本商品的”。

### 3.10 `recommend(self, request)` · L328（主流程）

**参数**：

| 参数 | 类型 | 含义 / 取值 |
| --- | --- | --- |
| `request` | `RecommendationRequest` | 字段：`trace_id/user_id/session_id/timestamp/source`（元信息）、`intent`（六种意图）、`constraints`（约束）、`preferences`（反馈）、`item_ids`（点名商品）、`top_k`（1~24） |

**返回**：`tuple` 两个值：

1. `items`：`list[RecommendationItem]`，按分数降序的前 `top_k` 件，每件带 `sources/score/score_breakdown/evidence`；
2. `diagnostic`：`dict`，固定 6 个键：

| 键 | 含义 |
| --- | --- |
| `mode` | `'hybrid'` / `'offline_demo'` |
| `warnings` | 降级原因列表 |
| `recall_count` | 进入候选的商品数 |
| `filtered_count` | 被硬约束筛掉的数量 |
| `rejected` | `[{item_id, reasons}]`，被拒明细 |
| `candidates` | `[{item_id, sources}]`，每个候选的来源 |

**怎么做（五步）**：

1. **① 上游召回**：`upstream, warnings, mode = self._recall_upstream(request)`；
2. **② 多路召回**：`routes = {每个商品ID: {'popularity'}}`，再给命中的候选加
   `category` / `context_tags` / `similarity` / `module_one_http` 来源；真实目录 hybrid 时候选只听上游；
   `explain/compare` 意图只取点名的商品；`similar` 只保留相似路由；
3. **③ 硬约束过滤**：逐个候选跑 `_hard_failures`，有原因就记进 `rejected` 并跳过；
4. **④ 打分 + 证据**：`_score_breakdown` 算六项，`sum()` 四舍五入 6 位作为总分，`_evidence` 造证据包；
5. **⑤ 排序 + TopK**：`items.sort(key=(-score, item_id))`，同分按商品 ID 升序，然后 `items[:request.top_k]`。

**会出错吗**：`item_ids` 里有目录中不存在的商品 → `ITEM_NOT_FOUND`；上游问题不抛，只进 `warnings`。

**口播**：
> `recommend` 接收推荐请求，返回两样：排好序的商品，和一份诊断信息（召回了多少、筛掉多少、被拒原因、每个候选来源）。
> 五步：先问上游，再把全目录放进候选并打来源标记，然后跑硬约束、算六项分、造证据，最后按分数降序
> 同分按商品 ID 升序排，取前 top_k 个。

### 3.11 本文件口播（90 秒，可直接念）

> 这个文件有三个部分：`Catalog` 读并校验商品目录，`get` 按 ID 取商品；
> `RecommendationAdapter` 是核心，`_recall_upstream` 问模块一要候选（失败只记警告降级），
> `_hard_failures` 判断四个硬约束，`_score_breakdown` 算六项分，`_evidence` 造证据包，
> 最后 `recommend` 把五步串起来：召回 → 打来源 → 硬过滤 → 打分造证据 → 排序取 TopK。

## 8. 被追问时的 8 个短答

1. **为什么参数都要显式传、不用全局变量？** 方便测试替换（假上游、假会话、临时目录），也避免状态互相污染。
2. **`remote` 参数为什么要能注入？** 为了做故障注入：验收/单测传一个必抛超时的假上游，验证降级分支。
3. **`mode` 参数在打分里干嘛？** 决定热门项是否参与：真实目录 + 上游可用时，热门记 0，避免合成热度干扰真实排序。
4. **`targets` 参数为什么是列表？** `compare` 可能点名多个商品；`similar` 只取第一个算相似度。
5. **`sources` 为什么要 `sorted()`？** 输出顺序稳定，同一输入两次结果才能逐字节一致。
6. **`known` 参数在 `_prices` 里干嘛？** 只统计商品表里有的 ID，避免生成没有名字的孤儿商品。
7. **`output` 参数能省吗？** 不能，验收要求“生成物 + 证据”都要落盘，且下次启动可以直接复用。
8. **测试里的 `demo-001` 算不算写死商品 ID？** 不算业务代码：测试数据是固定的 18 件合成商品，断言需要一个确定商品；业务路径全部从目录读。
