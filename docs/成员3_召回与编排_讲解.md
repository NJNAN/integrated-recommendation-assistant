## 0. 用 60 秒知道你在干什么

这个项目是一个**会听人话的购物推荐机器人**。

用户输入一句话，比如：

> 「我想买一个蓝色背包，300 块以内」

机器人要做七件事：

1. 听懂这句话，找出三个条件：**背包**（品类）、**蓝色**（颜色）、**300 块以内**（预算）。
2. 从商品库里，把可能相关的商品**先都拿出来**。
3. 把不符合条件的（不是背包的、不是蓝色的、超过 300 块的）**全部放回去**。
4. 给剩下的商品**打分**，按分数从高到低**排队**。
5. 只把排在最前面的几个（默认 6 个）**拿给用户看**。
6. 每个商品配一句「为什么推荐它」，而且这句话必须有真实依据（价格、颜色、描述都得是商品库里原本就有的）。
7. 用户点「喜欢」，下次这个商品（以及相似商品）就往前排。

**你负责第 2、3、4、5 步，外加把整个流程串起来。**
第 1 步是同学2 的活，第 6 步是同学4 的活，第 7 步是同学5 的活。

### 记住这个比方就够了

> **你是超市导购。** 客人说：蓝色背包、300 以内。
>
> 你先把货架上所有商品扫一眼（**召回**）；
> 把不是背包、不是蓝色、超过 300 的都放回去（**硬约束**）；
> 剩下的按「这商品最近卖得好不好 + 客人以前喜欢什么」排队（**打分**）；
> 最后只拿 6 个给客人（**TopK**）；
> 每个都附一句「这是蓝色、229 元、在您预算内」（**证据/解释**）。
>
> 如果仓库系统坏了（我们叫「**上游**」坏了），你也不能空手站在那儿——
> 就按「最热门的商品」先推荐（**降级**）。

### 4.1 `orchestrator.py` —— 总调度（也回答你问的 `_handle`）

**这个文件像餐厅的前台。**

客人来了（一条请求进来），前台不会自己炒菜，而是按顺序把单子交给后厨各个环节：
验单 → 看客人要什么 → 查这桌之前点过什么 → 确认没矛盾 → 交给选品 → 交给讲解 → 出餐。

#### `handle` 和 `_handle` 是什么关系

代码就在文件第 29–34 行，一共 6 行：

```python
def handle(self, data):          # 对外的大门
    with self.lock:              # 上锁：一次只让一个人进来
        return self._handle(data)  # 进来后，交给后厨流程

def _handle(self, data):         # 后厨流程（真正干活的地方）
```

逐行翻译：

- `handle`：**接待窗口**。只有 3 行，做的事是「上锁，然后把活转给 `_handle`」。
- `with self.lock`：**上锁**。因为网页可能同时来好几个请求（多线程），不加锁的话两个用户的条件会互相覆盖。
  加了锁，就变成「一次只处理一个，处理完再放下一个」。
- `_handle`：**真正的主流程**，从第 67 行一直到文件末尾（254 行），一条请求从这里开始走到结束；其中 12 个步骤在第 128–236 行。
- 前面加下划线 `_` 是 Python 的习惯：**内部方法**，意思是「外面的人请只调 `handle`，别直接调 `_handle`」。

一句话记住：

> **`handle` 是接待窗口（加锁），`_handle` 是后厨流水线（真正的 12 个步骤）。**

#### `_handle` 里的 12 个步骤（每一句都翻译成人话）

代码里我用 ①~⑫ 写了注释，行号在最后一列，方便你指给老师看。

| 步 | 人话 | 代码行号 |
| --- | --- | --- |
| ① | 检查这张工单填得对不对（缺字段就退回，错误码 `INVALID_EVENT`） | L128 |
| ② | 听懂用户想干嘛（交给同学2 的 `understand`） | L204 |
| ③ | 拿出这桌之前的点单记录，并**拍张照存起来**（为了出错能恢复） | L137 |

#### 里面还有两个小工具

- `record(...)`（第 94 行）：**记流水账**。每走一步就写一行「第几步、现在几毫秒、当时的数据」。
  这些流水账最后会变成响应里的 `trace`（老师问「可追踪」就是看这个）。
- `finish(...)`（第 111 行）：**收尾**。写状态、写文案、记总耗时，返回响应。

#### 出错了怎么办

- 第 237 行：遇到「业务错误」（比如商品不存在）→ 返回错误码，并把会话**恢复到第 ③ 步存的快照**（回滚）。

这就是为什么「失败的请求不会污染会话」：**改之前先拍照，错了就恢复。**

### 4.2 `recommendation.py` —— 挑货和排队（你最核心的文件）

这个文件干三件事：**把货拿齐、把不合格的放回去、给剩下的排队。**

#### 第一步：`recommend()` 的五步（第 328 行起）

```python
def recommend(self, request):
    upstream, warnings, mode = self._recall_upstream(request)   # ① 问隔壁模块一要推荐
    routes = {每件商品: {'popularity'}}                           # ② 先把所有商品都放进候选
    ...给候选打上「品类/标签/相似/上游」等来源标记...
    for 每件候选:
        if 不满足硬约束: 记到 rejected，跳过                # ③ 筛条件
        算分 breakdown = self._score_breakdown(...)                # ④ 打分
        准备证据 evidence = self._evidence(...)                     #    顺便做证据袋
    按 (-分数, 商品ID) 排序，取前 top_k 个                         # ⑤ 排队 + 只留前 K
```

翻译成人话：

1. 先问隔壁模块一「你觉得该推什么」（问不到就降级，不算失败）。
2. 把商品库里**所有**商品先放进候选篮子，每件记上它「从哪来」。
3. 一件件检查，不符合条件就扔掉，并记下「为什么扔」（这个记录叫 `rejected`）。
4. 合格的算分、做证据袋。
5. 排序，只留前 K 个。

#### 第二步：硬约束（第 191 行，很短但最重要）

```python
failures = [key for key in ('category', 'color')
            if key in constraints and product[key] != constraints[key]]
price = product['price']
if price is None and 用户给了预算:      failures.append('missing_price')
elif price is not None and (价格 < 最低预算 or 价格 > 最高预算):
                                       failures.append('budget')
```

人话：

- 用户要了品类/颜色，商品对不上 → 记一笔 `category` / `color`。
- 商品没有价格，用户又给了预算 → 记一笔 `missing_price`（没依据就不推）。
- 价格超出预算 → 记一笔 `budget`。
- 只要有任意一笔，这件商品就直接扔掉。

**为什么一定要在打分之前做？** 因为如果先打分再筛，就可能出现「某个商品分数很高，但它超预算，结果还是被推出来」。
老师问「硬约束不被排序分数覆盖」就是问这个：**先筛后打分，分数再高也覆盖不了规则。**

#### 第三步：打分公式（第 225 行，老师最爱问）

每个商品得分 = 下面六项加起来（权重就是我们自己定的，写死在代码里，每一分都能解释）：

| 项 | 算什么 | 人话 | 为什么要有它 |
| --- | --- | --- | --- |
| `popularity` 热门 | `0.4 × 热度` | 越多人买过越靠前 | 没有偏好的时候先推热门 |
| `context` 场景 | `0.2 × 命中几个（对象/场景）` | 用户说「送朋友」「通勤」，符合就加分 | 软偏好，不是硬条件 |
| `similarity` 相似 | `0.3 × 同品类 + 0.1 × 共同标签数` | 用户说「找相似的」时才用 | 支持「和这个像的」 |
| `upstream` 上游 | `0.3 × 隔壁给的分数`（真实商品模式下用 1.0） | 借隔壁推荐系统的排序结果 | 复用模块一的能力 |
| `feedback` 反馈 | `2.5 × 点赞(+1) 或 倒踩(-1)` | 用户点过赞的商品猛往前排 | 让用户立刻看到反馈效果 |
| `tag_affinity` 标签亲和 | `0.06 × 共同标签数 × 符号` | 喜欢「背包」会稍微带动别的背包 | 让偏好能扩散一点 |

**两个能当场手算的例子：**

```text
例1：云朵轻量双肩包，热度 0.92
     得分 = 0.4 × 0.92 = 0.368，其他五项都是 0

例2：给「墨色无线键盘」点赞
     点赞前：0.4 × 0.85 = 0.34，排第 10
     点赞后：0.34 + 2.5 = 2.84，排第 1
     另外和它共享标签的商品（保温杯、机械键盘）各 +0.06
```

#### 第四步：为什么同输入一定同输出（老师会问「可复现」）

排序那句话是：

```python
items.sort(key=lambda item: (-item.score, item.item_id))
```

人话：**先按分数从高到低排；分数一样的，按商品编号排。**

- 没有随机数（我们不掷骰子）。
- 没有用时间、也不用「谁先来谁先排」。
- 所以同一句话、同样的商品库，跑两次结果一模一样。
- 验收时就是跑两次，把结果算个「指纹」（sha256），两次指纹相同 → 证明一样。

#### 第五步：证据袋（为什么要给每个商品做档案）

`_evidence()`（第 279 行）给每件商品准备：

- 商品属性（名字、价格、品类、颜色）
- 从哪几路召回来的（`sources`）
- 命中了哪些条件（预算、颜色…）
- 证据片段（比如「描述：轻量双肩设计，设有独立收纳隔层」）

为什么要做？因为同学4 写解释时**只允许读这个档案袋**，档案袋里没有的东西不许说。
所以「解释不编造」这件事，是你在这一步先把依据备齐的。

### 4.3 `module_one.py` —— 商品数据从哪来

隔壁模块一有一份**商品表**（2,208 件真实商品）和一份**历史交易记录**（谁在什么时候买了什么、多少钱）。
你的任务是把这两份文件合成一份我们能用的商品清单。

三条规则（老师可能会问）：

1. **价格**：取这件商品**最后一次被卖出去的价格**（单位英镑），不是现在的售价。
   界面上必须写清楚这一点，否则就是误导用户。
2. **颜色**：只从英文商品描述里找颜色词（BLUE→蓝色）。找到唯一一个就用它；
   找到好几个就写「多色」；一个都没有就写「未标注」。**不允许猜。**
3. **没有价格的商品**：写「价格缺失」，并且**带上预算条件时不许推荐它**（因为没依据）。

另外每个商品都会记下「价格来自哪个文件、哪一天」，这叫**来源可追溯**。

#### `integrated_settings()`：启动时决定用真数据还是假数据

- 仓库里有隔壁模块一的代码 → 用真实商品（2,208 件）。
- 没有 → 用 18 件合成商品（专门用来测试的假数据）。
- 这叫「**降级**」：不管有没有隔壁项目，页面都能跑起来。

### 4.4 `scripts/03_orchestrator_demo.py` —— 4 个体检

这个脚本就是你的「验收报告生成器」。它跑 4 个测试，把结果写进 `outputs/stage03_demo.json`。

| 体检项目 | 人话 | 期望 |
| --- | --- | --- |
| 正常推荐 | 蓝色背包 300 以内，能不能返回符合条件的商品 | 返回 2 件，都是蓝色背包、都不超 300 |
| 硬约束空集 | 耳机预算 1 元，会不会偷偷放宽预算 | 0 件 + 提示「请调整条件」，预算条件还在 |
| 上游超时降级 | 假装隔壁服务挂了，还能不能给结果 | 还能返回 2 件，只是多一条「已降级」警告 |
| 确定性复现 | 同一句话跑两次，结果一不一样 | 两次结果指纹（sha256）完全相同 |

跑法就一行：

```powershell
python -B scripts/03_orchestrator_demo.py
```

看到 `阶段03: 4/4 PASS` 就对了；有失败会直接报错退出，不会假装修好。

那个「假装隔壁挂了」是怎么做的？脚本里有一小段：

```python
class TimeoutRemote:                    # 假的隔壁服务
    def recall(self, request):
        raise AdapterError('UPSTREAM_TIMEOUT', '上游超时')   # 一叫它就故意超时
```

然后把它传给推荐模块，就等于「上游必挂」。这是测试里常用的手法，叫**故障注入**。

## 5. 老师可能问的 10 个问题（人话答案）

**Q1：你负责哪一块？**
> 用户说一句话之后，到「返回几件商品」之间的部分：把候选找出来、筛掉不符合条件的、算分排队、取前几个，以及把整个流程串起来。

**Q2：什么是召回？为什么不直接把所有商品排序？**
> 召回就是「先把可能相关的都找出来」。18 件时可以全排，但真实系统有几十万件，全排太慢，
> 所以先按几种「来路」（热门、同品类、相似、隔壁推荐）各拿一批，合起来再筛。

**Q3：为什么先筛条件再打分？**
> 因为预算是硬规则，不是偏好。先打分的话，可能出现超预算但分数高、照样被推出来。
> 先筛后打分，被筛掉的还会记录原因（`rejected`），可以解释给用户看。

**Q4：没有结果怎么办？会不会放宽条件？**
> 不放宽。返回 0 件 + 一句人话提示「请调整条件或撤销上一步」，用户的条件原样保留。
> 老师如果问「为什么」，答：放宽条件等于骗用户，宁可让他自己改。

**Q5：隔壁推荐服务挂了怎么办？**
> 降级：记一条警告（原因码 `UPSTREAM_TIMEOUT`），候选改用「热门」来排，条件照旧生效。
> 用户仍然能拿到结果，响应里会标「已降级」。
>
> 详细版（触发条件、只变哪几个字段、现场验证命令）：[超时与降级说明.md](超时与降级说明.md)。

**Q6：为什么同样的输入两次结果一样？**
> 排序规则是「分数从高到低，分数一样按商品编号」，没有随机数，也不依赖时间。
> 验收时跑两次算指纹（sha256），两次一样。

**Q7：打分那六项是怎么定的？**
> 是经验规则，不是训练出来的模型：热门 0.4、场景 0.2、相似 0.3+、上游 0.3、反馈 2.5、标签 0.06。
> 每一项都能单独解释「为什么它加分」。真正的模型在隔壁模块一，我们只是把它的分数当一项用。

**Q8：什么是 trace？为什么要有？**
> 就是流水账：一次请求里每一步都记「第几步、花了多少毫秒、当时的数据」。
> 出问题时能一眼看出是哪一步坏的；老师要求「可追踪」就是看这个。每一次请求有个编号 `trace_id`，从头到尾不变。

**Q9：你的代码里有写死商品 ID 或路径吗？**
> 业务代码里没有。路径、端口、阈值都在 `config/settings.py`；商品全部从商品库读。
> 测试里用的 `demo-001` 是测试数据的固定编号，目的是让断言稳定，不是演示答案。

**Q10：如果让你加一路新的召回（比如「新品优先」），要改哪里？**
> 在 `recommend()` 里加一个来源标记和一条规则，再给个权重就行。
> 因为每件商品的来源本来就记在 `sources` 里，加完自动会出现在证据和解释里。
