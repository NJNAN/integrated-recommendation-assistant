# 成员3 · 召回与编排：你需要理解什么

> 你负责**把用户的条件变成一份可解释、可复现、可降级的推荐结果**。
> 文件：`assistant/module_one.py`(132)、`assistant/recommendation.py`(181)、`assistant/orchestrator.py`(144)、
> `scripts/03_orchestrator_demo.py`(65)、`tests/test_recommendation.py`(90)，共 612 行。
> 答辩你只需要讲 3 件事：**数据从哪来（召回）、谁说了算（硬约束+打分）、怎么串起来（编排/降级）**。

## 1. 你在系统里的位置

```text
浏览器/接口 ──事件──► Orchestrator（你的模块）
                         │ 1. 校验事件、取意图和会话（别人模块的 understand/session）
                         │ 2. 组装 RecommendationRequest（四类契约之一）
                         ▼
                 RecommendationAdapter（你的模块）
                         │ 3. 多路召回：popularity / category / context_tags / similarity / 模块一上游
                         │ 4. 硬约束过滤：品类、颜色、预算、缺失价格 —— 先过滤，后打分
                         │ 5. 打分：6 项加权 → 稳定排序 → TopK
                         │ 6. 给每件商品装 EvidencePack（解释模块只认这个）
                         ▼
                 推荐结果 + diagnostic ──► 解释（别人模块）──► 统一响应 + trace
```

一句话：**上游给候选和分数，你负责过滤、排序、留痕，并在上游挂掉时用离线目录顶上。**

## 3. 八个必须理解的概念（每个 1 句话 + 代码位置）

1. **四类契约里你管两头**：进是 `RecommendationRequest`（意图/约束/偏好/目标商品/TopK），
   出是 `RecommendationItem` + `EvidencePack`（属性/来源/分数明细/证据片段）。见 `contracts.py`。
2. **多路召回 + 来源可追溯**：候选来自热门、品类命中、对象/场景标签、相似商品、模块一上游；
   每件商品的 `sources` 列表记录它被哪几路召回（验收点“候选来源可追溯”）。
3. **硬约束先于打分**：品类/颜色/预算/缺失价格在 `_hard_failures` 里先判死，被过滤的进 `diagnostic.rejected`；
   打分只在活下来的候选里做。所以“高分商品不可能突破预算”。
4. **打分是 6 项可解释加权**：`_score_breakdown` 返回热门、上下文、相似度、上游、反馈、标签亲和六项，
   `score = round(sum(六项), 6)`；每一项都能单独讲给老师听。
5. **确定性**：排序键 `(-score, item_id)`，同分按商品 ID 兜底；没有任何随机数，所以同输入必得同结果
   （阶段3 的“确定性复现”用例就是两次跑、比 sha256）。
6. **上游降级**：`_recall_upstream` 捕获 `AdapterError/ContractError/OSError/TimeoutError`，
   转成 `warnings` + `mode='offline_demo'`，继续用 popularity 召回；**硬约束照样生效**。
7. **编排是唯一入口**：`Orchestrator.handle` 加锁串行；每一步写一条 `trace`（event→intent→context→request→
   recall_and_ranking→explanation→result）；出错时用会话快照 `restore` 回滚，返回六种 status 之一。
8. **真实目录是“生成物+证据”**：`import_catalog` 把模块一 `catalog.csv` 和 `train.csv` 合成
   `data/module_one_catalog.json`，保留 GBP 历史单价、颜色来源、来源文件 sha256、缺失价格标注。

## 4. 代码怎么走（按函数，能指着屏幕讲）

### `recommendation.py::recommend` —— 五步

```python
1  upstream, warnings, mode = self._recall_upstream(request)      # 上游候选/降级
2  routes = {item_id: {'popularity'} ...}; 加 category/context_tags/similarity
3  for item_id, sources in routes.items():                        # 逐候选
       failures = self._hard_failures(product, constraints)       # 硬约束
       if failures: rejected.append(...); continue                # 被拒留痕
       breakdown = self._score_breakdown(...)                     # 打分
       evidence = self._evidence(...)                             # 证据包
       items.append(RecommendationItem(...))
4  items.sort(key=lambda item: (-item.score, item.item_id))       # 稳定排序
5  return items[:request.top_k], diagnostic                        # TopK + 诊断
```

- `_recall_upstream`：没配上游 → `OFFLINE_DEMO` 警告；有上游 → 只保留与本目录 ID 一致、
  用 `max()` 去重取最高分；上游返回的 ID 与目录**零交集** → `INVALID_UPSTREAM`
  （宁可不推荐，也不编造价格和属性）。
- `_hard_failures`：`category`、`color` 必须相等；`price is None` 且带预算条件 → `missing_price`；
  价格越界 → `budget`。返回字符串列表，直接写进 `rejected[].reasons`。
- `_score_breakdown`（**背下来**，权重是答辩必问）：

  | 项 | 公式 | 说明 |
  | --- | --- | --- |
  | popularity | `0.4 × popularity` | 真实目录 hybrid 模式记 0（不拿合成规则干扰真实排序） |
  | context | `0.2 × (对象命中 + 场景命中)` | 0 / 1 / 2 次命中 |
  | similarity | `0.3×同品类 + 0.1×共同标签数` | 只在 `similar` 意图计算 |
  | upstream | `0.3 × 上游分数`（真实目录 hybrid 为 `1.0`） | 模块一冻结排序的分数 |
  | feedback | `2.5 × 该商品反馈(+1/-1)` | 阶段5 排名变化靠它 |
  | tag_affinity | `0.06 × Σ 反馈商品与自己共同标签数` | 喜欢“背包”会稍微带动别的背包 |

- `_evidence`：装 `attributes`（名称/价格/品类/颜色/币种/价格类型）、`matched_constraints`、
  `visual_labels`（只留置信度 ≥ 0.7 的）、`snippets`（`catalog:<id>:attributes`、`:description`，
  真实目录再加 `:provenance`）。**snippet id 前缀必须带 item_id**，这是解释模块校验引用归属的依据。

### `orchestrator.py::_handle` —— 一条事件的 12 步

1. `InteractionEvent.from_dict` 校验（非法 → `INVALID_EVENT`）
2. `understand` 出意图/槽位/缺失/冲突
3. 取会话 + 存快照（用于回滚）
4. `end/reset` → 清理会话，`status=ended`
5. `undo` → 撤销上一轮约束
6. 意图内冲突 → `conflict`
7. 预算币种与目录不一致（如人民币预算 vs GBP 目录）→ `needs_clarification`，不自动换算
8. 必选槽位缺失 → `needs_clarification`（例如“找类似的”没给商品）
9. 合并会话约束，预算上下界冲突 → `conflict`，不写状态
10. 反馈分支：`apply_feedback` 覆盖偏好（不累加）；其它分支：校验目标商品存在（`ITEM_NOT_FOUND`）
11. 组装 `RecommendationRequest` → 推荐 → 逐条 `explain` → 写 `last_item_ids`
12. 空结果 → `status=empty` + 提示“调整条件”；否则 `ok`

异常路径：`ContractError` → `error` + 快照回滚；其它异常 → `INTERNAL_ERROR` + 回滚。
响应固定字段：`trace_id/status/message/items/context/degraded/warnings/error/trace/elapsed_ms`。

### `module_one.py` —— 真实目录与服务

- `_prices`：跳过退货单（`InvoiceNo` 以 `C` 开头）、非正数价格/数量；日期必须是 ISO（否则直接报错，
  避免按错误日期排序）；每个商品保留**最后观测**的单价和交易次数。
- `import_catalog`：名称取 `name` 或英文描述；颜色由描述里的颜色词判断（唯一→该颜色，多个→“多色”，
  没有→“未标注”）；品类用 MUG/CUP、UMBRELLA、RUCKSACK 等名词覆盖；`popularity = 次数 / 峰值`；
  `tags=[品类, 原品类]`；输出文档带 `dataset/model_version/price_notice/dataset_reference/sources(sha256)`。
- `ModuleOneService`：先探测 5001 端口（避免静默失败）→ 起 `integrations/module_one_server.py` 子进程 →
  轮询 `/api/health` 直到 `model_ready`（20 秒超时）→ 关闭时 terminate/kill。
- `integrated_settings`：`IRA_PROFILE=demo`、显式 `IRA_CATALOG/IRA_RECOMMENDER_URL`、或缺少模块一文件 →
  返回 `(settings, None)` 走离线；否则导入目录 + 指向本机 5001 + 超时改 5 秒。

## 6. 两分钟逐字稿（可直接背）

> 我负责的是“召回与编排”，也就是从用户条件到推荐结果这一段。
> 输入是 `RecommendationRequest`，里面有意图、硬约束、会话偏好和目标商品。
> 第一步是多路召回：热门商品、品类命中、对象/场景标签命中、相似商品，加上模块一真实推荐服务的候选，
> 每一件商品的 `sources` 都记录它从哪几路来，所以候选来源可追溯。
> 第二步是硬约束过滤：品类、颜色、预算、以及缺失价格，在打分之前就判死并写进 `rejected`，
> 这样高分商品不可能突破预算。
> 第三步打分，六项加权：热门 0.4、上下文 0.2、相似度 0.3、上游分数 0.3、反馈 ±2.5、标签亲和 0.06，
> 每一项都写进 `score_breakdown`，所以排序结果可解释。
> 最后按“分数降序、商品 ID 升序”稳定排序取 TopK，保证同一输入必得同一结果，我们有一条用例专门比 sha256。
> 上游挂掉时，比如超时，会记录 `UPSTREAM_TIMEOUT` 并降级成离线热门召回，硬约束仍然生效。
> 编排层是唯一入口：校验事件、取会话快照、合并约束、组装请求、调用推荐、再交给解释模块，
> 每一步写一条 trace；出错就用快照回滚，状态只有 ok、empty、追问、冲突、结束、错误六种。
> 真实目录这边，我把模块一的商品表和历史交易合成一份带证据的目录：价格是英镑历史最后观测单价，
> 缺失价格明确标注，颜色只从英文描述里取，来源文件带 sha256。

## 7. 老师可能追问（准备好这 8 个）

1. **为什么先过滤再打分？** 硬约束是业务规则，不能因为热门或上游分高就被覆盖；空集也不放宽，
   而是返回 `empty` 让用户调整或撤销。
2. **Why TopK 用 `(-score, item_id)`？** 分数相同时需要一个确定的次序，商品 ID 天然稳定，
   这样同输入必得同输出，验收里能用 sha256 证明。
3. **上游分和你的分怎么融合？** 上游只是六项之一（权重 0.3；真实目录模式 1.0），
   所以它影响排序但不能越过硬约束；上游 ID 与目录无交集时直接 `INVALID_UPSTREAM`，不编造价格。
4. **降级会不会改变用户条件？** 不会。降级只影响候选来源和 `degraded/warnings`，
   约束、偏好、TopK 都不变；阶段3 的超时用例专门断言了这点。
5. **为什么真实目录模式把 popularity 权重置 0？** 合成目录的热门分和真实排序不是一套口径，
   真实模式下以模块一冻结排序为主，避免两种排序互相干扰。
6. **反馈为什么是 ±2.5，这么大？** 热门这一项的总分差最多只有 0.4 分（popularity 在 0~1 之间），
   反馈 ±2.5 才能让用户明显看见排名变化；重复反馈是覆盖不是累加，所以不会无限放大。
7. **相似度怎么算的？** `similar` 意图下：同品类 +0.3，每个共同标签 +0.1，并把候选集限制在相似路由里。
8. **证据包是干什么的？** 解释模块只允许引用 `EvidencePack` 里的事实，snippet id 必须带本商品前缀，
   缺片段或属性不一致就停止解释——所以“解释不编造”是你在这一层先把证据备齐的。

## 10. 三个容易被问倒的点（提前想好）

1. **“你这个打分是模型吗？”** 不是，是可解释的加权规则；真正的学习模型是模块一的排序，
   它的分数作为 `upstream` 一项并入。规则的好处是每一步都能给出理由和证据。
2. **“18 件合成商品的通过率说明什么？”** 只说明契约、过滤、降级、可复现这些流程正确，
   不代表真实推荐效果；真实效果要看模块一的训练评估，不能拿这里的 57/57 当准确率。
3. **“如果让我加一路召回呢？”** 在 `recommend` 里加一个路由（例如“新上架”+`sources.add('fresh')` 并给权重），
   `sources` 和 `score_breakdown` 会自动把它带进证据和解释，不需要改协议。
