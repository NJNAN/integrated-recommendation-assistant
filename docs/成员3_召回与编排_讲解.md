### 2.2 数据流与失败出口（任务书 2）

**trace_id 怎么贯穿**：响应顶层的 `trace_id`、每一段 `trace[]`、每一件 `items[].trace_id` 三者相同。
7 个阶段固定顺序：

```text
event → intent → context → request → recall_and_ranking → explanation → result
```

每条 trace 项 = `{trace_id, stage, elapsed_ms, data}`，`elapsed_ms` 是相对本次请求开始的耗时。

**主要字段**（响应顶层）：

| 字段 | 含义 |
| --- | --- |
| `status` | 六种状态之一：ok / empty / needs_clarification / conflict / ended / error |
| `message` | 给人看的中文提示 |
| `items[]` | 商品（含 `sources`/`score`/`score_breakdown`/`evidence`/`explanation`） |
| `context` | 会话快照：constraints / preferences / last_item_ids / top_k |
| `degraded` + `warnings[]` | 是否降级、降级原因码 |
| `error` | `{code, message}`，只有出错时非空 |
| `mode` / `dataset` / `currency` / `price_notice` | 当前数据口径 |

**失败出口一览**（任务书要求“标明失败出口”）：

| 失败出口 | 错误码 | HTTP | 谁产生 |
| --- | --- | --- | --- |
| 事件缺字段/枚举错/模态 payload 错 | `INVALID_EVENT` | 400 | 成员1 的契约 |
| 目标商品不在目录 | `ITEM_NOT_FOUND` | 400 | 你的 `Catalog.get` |
| 目录本身脏（缺字段/价格标注错/ID 重复） | `INVALID_CATALOG` | 400 | 你的 `Catalog.__init__` |
| 上游候选与本目录无交集/格式错 | `INVALID_UPSTREAM` | 不进 error，进 `warnings` | 你的 `_recall_upstream` |
| 上游超时/不可用 | `UPSTREAM_TIMEOUT` / `UPSTREAM_UNAVAILABLE` | 同上 | 你的 `_recall_upstream`（**不抛异常**） |

## 3. 步骤2：实现多路召回适配

> 任务书原文：
> 1. 统一候选字段并保留 sources、score、evidence，完成去重和 TopK 截断。
> 2. 函数或类须包含明确输入输出，不在入口脚本中堆放业务逻辑。
> 3. 对非法输入和缺失字段返回可解释错误。
> **本步证据：核心模块代码、单元或契约测试输出**

### 3.1 统一候选字段：sources / score / evidence 三件套

召回后每个候选都变成同一个 `RecommendationItem`（定义在成员1 的 `contracts.py`）：

| 字段 | 作用 | 来自哪 |
| --- | --- | --- |
| `sources` | 候选来源，可追溯（验收清单第 1 条） | `routes[item_id]` 集合 |
| `score` + `score_breakdown` | 总分 + 六项明细，可解释 | `_score_breakdown` |
| `evidence` | `EvidencePack`：属性、来源、命中约束、视觉标签、证据片段 | `_evidence` |
| `trace_id` | 与请求同一 ID | `request.trace_id` |

五条召回路由（`recommend()` L211–270）：

| 路由名 | 命中条件 | 为什么要有 |
| --- | --- | --- |
| `popularity` | 目录所有商品默认进候选 | 没有条件时也要有东西可推（冷启动） |
| `category` | 约束品类 == 商品品类 | 用户明确要品类时保证品类内优先 |
| `context_tags` | 约束里的对象/场景 ∈ 商品 tags | “给朋友/通勤”这类软偏好 |
| `similarity` | `similar` 意图下同品类或共享标签 | “找相似的”靠它 |
| `module_one_http` | 模块一真实推荐服务返回的候选 | 复用真实推荐系统的排序结果 |

> 真实目录 + 上游可用（hybrid）时特殊规则：**候选只保留上游给的那些**，避免合成热度混进真实排序。

### 3.2 去重与 TopK 截断

- **去重**：`routes` 用 `dict[item_id] -> set(sources)`，同一商品被多路召回只出现一次，来源合并成集合；
  上游同一商品返回多次时用 `max()` 取最高分（`_recall_upstream` L97–127）。
- **TopK**：`items.sort(key=(-score, item_id))` 后 `items[:request.top_k]`；`top_k` 来自会话（默认 6，上限 24）。
- 证据：`cases[0]` 的 `recall_count=18`（召回 18 个 item_id）→ `filtered_count=16` → items 2 件；
  单测 `test_ranking_is_deterministic_and_topk_is_applied` 断言 `top_k=3` 时正好 3 件。

### 3.3 输入输出明确 + 不在入口堆逻辑

| 层 | 负责 | 代码 |
| --- | --- | --- |
| 契约层 | 数据结构与校验 | `contracts.py`（成员1） |
| 业务层 | 召回/过滤/打分/证据 | `recommendation.py`：`Catalog` + `RecommendationAdapter`，每个方法单一职责 |
| 编排层 | 串流程、状态机、回滚 | `orchestrator.py::_handle` |
| 证据脚本 | **只做用例与断言**，不写业务 | `scripts/03_orchestrator_demo.py`（82 行：4 条用例 + sha256 比对 + 落盘） |

`request` 是 `RecommendationRequest`，`diagnostic` 固定 6 键
`mode/warnings/recall_count/filtered_count/rejected/candidates`。

## 4. 步骤3：硬约束过滤与上下文打分

> 任务书原文：
> 1. 实现预算、品类、颜色等硬约束过滤与会话偏好重排。
> 2. 记录输入、关键中间状态、输出与耗时。
> 3. 至少包含成功、边界和失败三类用例。
> **本步证据：三类链路 trace**

### 4.1 硬约束：四道闸门，在打分之前

`_hard_failures(product, constraints)`（L129–143）按顺序判断：

| 闸门 | 条件 | 拒绝原因 |
| --- | --- | --- |
| 品类 | 约束给了品类且不相等 | `category` |
| 颜色 | 约束给了颜色且不相等 | `color` |
| 缺失价格 | `price=None` 且用户给了预算 | `missing_price` |
| 预算 | 价格 < budget_min 或 > budget_max | `budget` |

**为什么必须在打分前**（验收清单第 2 条）：如果先打分再过滤，就存在“高分商品突破预算”的口子；
先过滤后打分，被拒的进 `rejected`，排序分数在规则面前不起作用。真实数据：

```text
"蓝色背包预算300以内" → rejected 里：
  demo-002 → ["color"]                        （背包但黑色）
  demo-003 → ["category", "color"]            （不是背包、不是蓝色）
  demo-006 → ["category", "color", "budget"]  （耳机 459，三重不符）
  demo-016 → ["color", "budget"]              （背包 399 绿色，颜色不符且超预算）
```

### 4.2 上下文重排：六项加权

`_score_breakdown`（L145–181）返回六项，`score = round(sum(六项), 6)`：

| 项 | 公式 | 说明 |
| --- | --- | --- |
| `popularity` | `0.4 × popularity` | 真实目录 hybrid 模式记 0 |
| `context` | `0.2 × (对象命中 + 场景命中)` | 0/1/2 次 |
| `similarity` | `0.3 × 同品类 + 0.1 × 共同标签数` | 仅 `similar` 意图 |
| `upstream` | `0.3 × 上游分数`（真实目录 hybrid 用 1.0） | 模块一冻结排序 |
| `feedback` | `2.5 × 该商品偏好(±1)` | **会话偏好重排** |
| `tag_affinity` | `0.06 × Σ 反馈商品共同标签数 × 符号` | **会话偏好重排（扩散）** |

**两个真实算例**（老师让你手算就用这两个）：

```text
① 正常过滤：demo-001 → 0.4×0.92 = 0.368，其余五项 0 → 排第 1
② 相似意图：对 demo-001 找相似，命中 demo-013
   popularity 0.4×0.86=0.344 + similarity (0.3 同品类 + 0.1×1 共同标签)=0.4 → 0.744
③ 点赞：给第 10 名 demo-010 点赞 → 0.34 + feedback 2.5 = 2.84 → 排名 10 → 1
   同时 demo-003/demo-009 因为共享标签各 +0.06（tag_affinity）
```

> 任务书要求的“会话偏好重排”就是 `feedback` + `tag_affinity` 这两项：阶段5 的反馈 A/B 对照就建立在这里
> （`stage05_feedback_ab.json` 的 `rank_change`）。

## 10. 追问准备（按任务书条目归类）

### A. 目标类（§一）

1. **“可追踪”具体指什么？** 响应 `trace_id`、7 段 `trace[].trace_id`、每件 `items[].trace_id` 三处一致，每段带 `elapsed_ms`。
2. **“可复现”怎么证明？** 排序键 `(-score, item_id)`、无随机数；`cases[3]` 两次跑 `items+context` 的 sha256 相同（`97a925cc…`）。
3. **“无结果降级”有几种？** 两种：上游不可用→热门召回（`warnings[0].code` 标明原因）；硬约束全拒→`empty` 且不放宽。

### B. 要求类（§二 6 条，每条一题）

4. **候选来源怎么追溯？** `sources` 集合 + `diagnostic.candidates`（item_id → sources 列表）。
5. **排序分数为什么覆盖不了硬约束？** 过滤在打分之前（`_hard_failures` 先跑），被拒项根本不进打分。
6. **空结果怎么提示？** `status=empty` + 固定文案（含“调整/撤销”）+ 约束保留。
7. **同输入同配置怎么保证？** 无随机、排序键含 `item_id`、目录只读、`top_k` 来自会话。
8. **关键路径不硬编码怎么保证？** 全部读 `config/settings.py`（路径/端口/TopK/阈值/上游地址/超时）；`module_one_root` 同级优先→`vendor/`。
9. **证据为什么可重跑？** 每条结论对应一个脚本；脚本失败非零退出；JSON 落盘带 `metrics`。

### C. 步骤类（§三）

10. **主链路哪一步最容易出错？** ⑩ 反馈/目标校验和 ⑨ 约束合并——所以这两个点先存快照，出错回滚。
11. **为什么 explain/compare 不走召回？** 只看用户点名的商品，省算力也避免推无关商品。
12. **去重在哪做的？** `routes` 用 dict + set，同一 item_id 只出现一次；上游重复用 `max()` 取最高分。
13. **TopK 从哪来、上限多少？** 会话 `ctx.top_k`（默认 6），payload 可给 1–24，越界 `INVALID_EVENT`。
14. **六项权重里哪两项是“会话偏好重排”？** `feedback`（2.5×偏好）和 `tag_affinity`（0.06×共同标签）。
15. **真实目录 hybrid 模式为什么 popularity 记 0？** 合成热度与真实排序不同口径，避免互相干扰。
16. **耗时记在哪？** `response.elapsed_ms`、每段 `trace[].elapsed_ms`、`metrics.latency_ms`（p50/p95/max）。

### D. 常见问题类（§五）

17. **业务代码里有没有写死商品 ID？** 没有；商品全部来自配置目录。测试夹具引用合成目录固定 ID 是为了断言确定数据。
18. **异常会不会被吞掉？** 不会：业务错误带 `error.code`，上游问题带 `warnings[].code`，内部异常兜底 `INTERNAL_ERROR`。
19. **只报了成功案例吗？** 4 条里 1 成功、1 空集、1 降级、1 复现；延迟报分位数。
20. **为什么上游失败不算 error？** 因为仍能给出结果（热门兜底）；这属于降级不属于失败，所以走 `warnings` + `degraded`。
