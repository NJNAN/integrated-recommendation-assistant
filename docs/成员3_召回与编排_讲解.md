## 5. 九个核心概念

### 5.1 四类契约里你管「两头」

- **进**：`RecommendationRequest(trace_id,user_id,session_id,timestamp,source,intent,constraints,preferences,item_ids,top_k)`
- **出**：`RecommendationItem`（商品事实 + sources + score + score_breakdown + evidence）
- **附带造**：`EvidencePack`（解释模块的唯一事实来源）
- 你不改协议；字段校验失败抛 `ContractError`，由编排层转成 `error` 响应。

一句话答法：「我只产出契约规定的东西，所以解释模块和前端不用关心我怎么排序的。」

### 5.2 多路召回（sources 可追溯）

五条路由，按命中方式打标：

| 路由 | 命中条件 | 为什么要有 |
| --- | --- | --- |
| `popularity` | 目录所有商品默认候选 | 没有条件时也要有东西可推（冷启动） |
| `category` | 约束品类 == 商品品类 | 用户明确要品类时保证品类内优先 |
| `context_tags` | 约束里的对象/场景 ∈ 商品 tags | 「给朋友」「通勤」这类软偏好 |
| `similarity` | `similar` 意图下同品类或共享标签 | 「找相似的」靠它 |
| `module_one_http` | 模块一真实服务返回的候选 | 复用真实推荐系统的排序 |

真实目录 + 上游可用（hybrid）时有特殊规则：**候选只保留上游给的那些**，避免合成热度混进真实排序。

一句话答法：「候选来源全记在 `sources` 里，验收点『候选来源可追溯』就是看这个字段。」

### 5.3 硬约束先于打分

`_hard_failures(product, constraints)` 按顺序判四件事：

```python
failures = [key for key in ('category','color') if key in constraints and product[key] != constraints[key]]
price = product['price']
if price is None and (给了 budget_min 或 budget_max): failures.append('missing_price')
elif price is not None and (price < budget_min or price > budget_max): failures.append('budget')
```

要点：
- 判定发生在**打分之前**，所以「分数再高也过不去」；
- 被拒的写进 `rejected[].reasons`，可以在证据里逐条解释；
- 空集**不放宽约束**，返回 `status=empty` 让用户调整或撤销；
- 缺失价格只有在用户给了预算时才被排除（不给预算时可以展示，但标注 `price_kind=missing`）。

一句话答法：「硬约束是业务规则不是排序偏好，必须在打分前面做成硬闸门。」

### 5.4 六项打分（可解释加权，不是模型）

`score_breakdown` 六项，`score = round(sum(六项), 6)`：

| 项 | 公式 | 取值来源 |
| --- | --- | --- |
| `popularity` | `0.4 × popularity` | 目录 popularity（0~1）；**真实目录 hybrid 模式记 0** |
| `context` | `0.2 × (对象命中 + 场景命中)` | 0 / 1 / 2 次匹配 |
| `similarity` | `0.3 × 同品类 + 0.1 × 共同标签数` | 仅 `similar` 意图 |
| `upstream` | `0.3 × 上游分数`；真实目录 hybrid 用 `1.0` | 模块一冻结排序 |
| `feedback` | `2.5 × 该商品偏好(+1/-1)` | 当前会话点赞/倒踩 |
| `tag_affinity` | `0.06 × Σ 反馈商品共同标签数 × 符号` | 喜欢「背包」会带动别的背包 |

一句话答法：「六项加权、每项都写进 `score_breakdown`，所以『为什么它排第一』永远答得出来。」

### 5.5 确定性

```python
items.sort(key=lambda item: (-item.score, item.item_id))
```

- 没有随机数、没有时间参与排序、没有字典顺序依赖；
- 同分用 `item_id` 兜底 → 同输入必得同输出；
- 验收用两个全新 `Orchestrator` 跑同一事件，比较 `items+context` 的 sha256（`stage03_demo.json` 的 `cases[3]`）。

一句话答法：「排序键是 `(-分数, 商品ID)`，所以同一输入两次跑出来的 JSON 哈希完全一样。」

### 5.6 上游降级（三层降级的第一层）

`_recall_upstream` 的三种结果：

| 情况 | 返回 | 响应表现 |
| --- | --- | --- |
| 没配上游（demo 模式） | `({}, [OFFLINE_DEMO], 'offline_demo')` | `warnings` 一条，其余照常 |
| 上游成功 | `(分数表, [], 'hybrid')` | `mode=hybrid`，候选来自上游 |
| 上游超时/不可用/格式非法 | `({}, [错误码], 'offline_demo')` | `degraded=true`，退回热门召回 |

要点：**降级只影响候选来源，不改约束、不改偏好、不改 TopK**。
上游给了 ID 但与本目录零交集 → `INVALID_UPSTREAM`（宁可不推，也不编造价格属性）。

三层降级具体是：① 上游不可用→离线召回；② 解释缺证据→解释模块降级不编造；③ 硬约束空集→不放宽，返回空集提示。

### 5.7 证据包（把「解释不编造」的防线前移）

- `attributes`：名称、价格、品类、颜色、币种、价格类型（解释模块逐字段比对）；
- `snippets`：`catalog:<item_id>:attributes`、`:description`，真实目录再加 `:provenance`；
- `visual_labels`：只保留置信度 ≥ `settings.visual_threshold`（0.7）的标签；
- `matched_constraints`：命中的约束，用来生成「符合当前条件：品类为背包…」。

一句话答法：「解释模块只允许引用我给的证据片段，片段 id 必须带本商品前缀，所以它编不出别的东西。」

### 5.8 编排是唯一入口（状态机 + trace + 回滚）

- 加锁串行（`RLock`），HTTP 多线程下也不会串会话；
- 每步 `record(stage, ...)` 写 trace，`trace[].trace_id` 全等于响应 `trace_id`；
- 出错前先存 `snapshot`，`ContractError` 时 `restore` 回滚，**失败请求不污染会话**；
- 六种状态：`ok / empty / needs_clarification / conflict / ended / error`。

### 5.9 真实目录是「生成物 + 证据」

`import_catalog` 把模块一 `catalog.csv`（商品表）和 `train.csv`（历史交易）合成一份目录：
- 价格取**每件商品最后一次正向交易的单价**，单位 GBP，`price_kind=historical_last_observed`；
- 颜色只从英文描述取颜色词（唯一才算，多个是「多色」，没有是「未标注」）；
- 每件商品带 `price_source`（文件名/日期/字段）、`color_source`（字段/tokens）、`popularity`；
- 文档级带 `model_version`、`price_notice`、`dataset_reference`、两个源文件的 sha256。

一句话答法：「真实目录不是抓来的，是用模块一的两份 CSV 生成、并且把每个字段的来源都记下来的。」

## 6. 逐函数精讲

### 6.1 `recommend()` —— 五步，全文骨架

```python
def recommend(self, request):
    catalog, constraints = self.catalog, request.constraints
    upstream, warnings, mode = self._recall_upstream(request)           # ① 上游（可能降级）
    routes = {item_id: {'popularity'} for item_id in catalog.items}      # ② 热门全量召回
    for item_id in upstream: routes[item_id].add('module_one_http')      #    上游候选并入
    if catalog.real and mode == 'hybrid':
        routes = {item_id: {'module_one_http'} for item_id in upstream}   # 真实模式只听上游
    targets = [catalog.get(item_id) for item_id in request.item_ids]      # 目标商品（不存在就报错）
    if request.intent in ('explain','compare'):                           # ③ 解释/对比不召回
        routes = {product['item_id']: {'requested_item'} for product in targets}
    else:
        for item_id, product in catalog.items.items():                    #    品类/标签/相似路由
            ...
    rejected, items = [], []
    for item_id, sources in routes.items():                               # ④ 过滤 + 打分 + 证据
        failures = self._hard_failures(product, constraints)
        if failures: rejected.append(...); continue
        breakdown = self._score_breakdown(...)
        evidence = self._evidence(...)
        items.append(RecommendationItem(...))
    items.sort(key=lambda item: (-item.score, item.item_id))              # ⑤ 稳定排序
    return items[:request.top_k], diagnostic
```

**边界细节（被追问时用）：**

| 细节 | 说明 |
| --- | --- |
| 上游重复 ID | `max()` 取最高分，不重复计入 |
| 上游分数非法 | `number(...,-1000,1000)` 校验，非法 → `INVALID_UPSTREAM` 并降级 |
| `explain` / `compare` | 只取 `requested_item`，不跑召回（省算力、也避免推无关商品） |
| `similar` 没有目标 | 产不出 similarity 路由，编排层会先拦成「追问」 |
| `similar` 有目标 | 路由只保留 similarity 命中的，避免「找相似」变成「全量推荐」 |
| 空路由 | `recall_count=0`，直接空集，不报错 |
| TopK | `items[:request.top_k]`；来自会话 `ctx.top_k`，默认 6、上限 24 |

## 8. 打分公式与四个真实算例

### 8.1 公式

```text
score = popularity + context + similarity + upstream + feedback + tag_affinity
      = 0.4·热门 + 0.2·(对象命中+场景命中) + (0.3·同品类 + 0.1·共同标签)
        + 0.3·上游分 + 2.5·反馈 + 0.06·Σ共同标签
```

### 8.2 算例 A：普通过滤（真实数据）

「蓝色背包预算300以内」，demo-001 云朵轻量双肩包：

```text
popularity = 0.4 × 0.92 = 0.368
其余五项 = 0
score      = 0.368        → 排第 1
```

### 8.3 算例 B：相似意图（真实数据）

对 demo-001 说「找相似的」，命中 demo-013 轻行运动双肩包：

```text
popularity = 0.4 × 0.86 = 0.344
similarity = 0.3 × 1（同品类） + 0.1 × 1（共同标签"背包"） = 0.4
score      = 0.744        → 显著高于普通候选
```

### 8.4 算例 C：点赞反馈（真实数据）

全目录 18 件里，给第 10 名 demo-010「墨色无线键盘」点赞：

```text
点赞前：popularity 0.34 → score 0.34 → 排名 10
点赞后：popularity 0.34 + feedback 2.5 → score 2.84 → 排名 1
附带影响：与它共享标签的商品各 +0.06
  demo-003 晨光随行保温杯（标签含"通勤"）→ tag_affinity 0.06
  demo-009 纸间机械键盘（标签含"办公"）→ tag_affinity 0.06
```

这就是「反馈后排序变化可解释」的证据：变化全部落在 `score_breakdown.feedback` 和 `tag_affinity` 两项上。

### 8.5 算例 D：真实目录离线（无上游）

「推荐红色杯子，预算10英镑以内」，真实目录 2208 件：

```text
recall_count = 2208      filtered_count = 2200（品类/颜色/预算拒掉 2200 件）
Top1：21238 红色复古波点杯子  £0.85  score = 0.4 × 0.1509 = 0.060369
```

真实目录 + 模块一服务在线（hybrid）时规则会变：`popularity=0`、`upstream=1.0×上游分数`，
候选只来自上游，避免合成热度干扰真实排序。

### 8.6 权重敏感性（老师问「换个权重会怎样」）

| 改动 | 效果 | 一句话解释 |
| --- | --- | --- |
| `top_k` 6 → 3 | 只返回前 3 件 | 数量由 `settings.top_k` 或请求 `top_k` 控制（1~24） |
| `visual_threshold` 0.7 → 0.4 | demo-008 的「绿色」标签（置信度 0.45）进入证据 | 阈值只管视觉标签是否可信，不影响硬约束 |
| 真实目录 hybrid | popularity 权重归 0 | 不让合成热门分干扰真实排序 |
| 去掉 `feedback` 项 | 点赞不再改变排名 | 阶段5 的 A/B 对照会失败，说明反馈项必要 |

## 11. 25 个追问与标准答案

### A. 设计类（为什么这么设计）

1. **为什么先过滤再打分？** 硬约束是业务规则不是偏好；先过滤保证「分数不能买通规则」，被拒项还能进 `rejected` 解释原因。
2. **为什么要多路召回，不直接全目录排序？** 合成目录 18 件、真实 2208 件还能扛，但真实系统候选是百万级；分路由既省算力又能解释「为什么它出现」。
3. **为什么打分是规则不是模型？** 规则每步可解释、可复现、无需训练；学习模型在模块一，它的分数作为 `upstream` 一项并入。
4. **为什么反馈权重 2.5 这么大？** 热门项总分差最多 0.4（0.4×popularity），反馈要能明显改变排名让用户看见；重复反馈覆盖不累加，所以不会放大。
5. **为什么真实目录 hybrid 时 popularity 记 0？** 合成热门分和真实排序不是一套口径，混在一起会破坏真实排序的可解释性。
6. **为什么 `explain`/`compare` 不走召回？** 它们只要用户点的那几件，跑全量召回既浪费又可能推出无关商品。

### B. 代码细节类（指着代码问）

7. **`recall_count` 和 `filtered_count` 是什么？** 前者是进入候选的路由数（合成 18、真实 2208），后者是被硬约束拒掉的数量（本例 16、真实例子 2200）。
8. **`sources` 是集合还是列表？** 内部用 `set` 去重，输出前 `sorted()` 保证顺序稳定。
9. **上游同一商品返回两次怎么办？** `max(score, 旧分)` 取最高，不重复计入。
10. **`score` 为什么 round 到 6 位？** 浮点累加会留 `0.36800000000000005` 这类尾巴，round 后 JSON 可复现、可比较。
11. **排序为什么用负分？** Python `sort` 升序，`-score` 就是降序；第二键 `item_id` 保证同分稳定。
12. **`top_k` 从哪来？** 会话里的 `ctx.top_k`（默认 `settings.top_k=6`），payload 可给 1~24，超范围 `INVALID_EVENT`。
13. **`Catalog` 为什么构造时就校验？** 脏目录越早失败越好，否则错误会以「价格缺失」「属性不一致」的面目出现在解释层。
14. **`EvidencePack` 的 snippet id 为什么带商品 ID？** 让解释模块校验「引用是不是本商品的证据」，防止张冠李戴。

### C. 数据类（数字要张口就来）

15. **真实目录多少件？多少没价格？** 2208 件，17 件缺失价格。
16. **1628 件没颜色怎么处理？** 标「未标注」，不猜；只有英文描述里明确出现颜色词才标颜色。
17. **价格单位是什么？** GBP，历史最后观测单价，不是现价；人民币预算会先澄清币种、不自动换算。
18. **popularity 怎么来的？** 交易次数 / 峰值交易次数（0~1 的归一化热度）。
19. **数据来源可追溯吗？** 是：目录记了 `dataset_reference`、两个源文件 sha256、每件商品的价格来源文件与日期。

### D. 边界/异常类

20. **上游超时会怎样？** `mode` 变 `offline_demo`、`warnings[0].code=UPSTREAM_TIMEOUT`、`degraded=true`，退回 popularity 召回，硬约束照旧。
21. **上游商品 ID 和目录完全对不上？** `INVALID_UPSTREAM` 并降级——不编造价格和属性。
22. **用户预算 0 会怎样？** 硬约束把所有商品拒掉 → `empty`，但会话约束保留 `budget_max: 0`，不放宽。
23. **非法反馈（对不存在的商品点赞）？** `apply_feedback` 抛 `INVALID_FEEDBACK`，编排层回滚快照，会话状态与上一次成功响应完全一致。
24. **预算 1 元买耳机？** 18 件全被拒（`budget`/`category`），返回空集 + 提示调整；证据里 `filtered_count=18`。

### E. 协作/甩锅类（不是你的模块，但要接得住）

25. **意图错了、约束抽错了算谁的？** 意图和槽位在成员2 的 `understanding.py`；我只做「缺失/冲突」拦截，不猜用户意图；若确实抽错，是规则词表要扩展。
（其余：解释生成→成员4；反馈写回→成员5；契约字段→成员1；HTTP 与错误码映射→成员5。见 15.4。）

## 15. 附录

### 15.1 统一响应字段（你负责填的加粗）

| 字段 | 含义 | 谁填 |
| --- | --- | --- |
| **`trace_id`** | 全链路追踪号 | 事件里的或新生成 |
| **`status`** | 六种状态之一 | 你（`finish`） |
| **`message`** | 中文提示 | 你 |
| **`items`** | `RecommendationItem` 数组 | 推荐模块 |
| **`context`** | 会话公开字段（约束/偏好/最近展示） | 会话模块，你在关键点回填 |
| **`degraded`** | 是否有降级 | 你（`bool(warnings)`） |
| **`warnings`** | 降级/离线原因码 | 推荐模块 |
| **`error`** | `{code,message}` | 你（异常分支） |
| **`trace`** | 阶段记录 | 你（`record`） |
| **`elapsed_ms`** | 总耗时 | 你（`finish`） |
| 可选 | `missing_slots` / `conflicts` / `mode` / `dataset` / `currency` / `price_notice` | 你 |

### 15.2 trace 阶段顺序

```text
event → intent → context → request → recall_and_ranking → explanation → result
（出错时最后一条是 error；每条都带 trace_id / stage / elapsed_ms / data）
```
